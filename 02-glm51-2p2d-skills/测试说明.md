# GLM-5.1 2P2D EFA 推理 — 测试说明

## 测试目的

客户在自建机房使用 ConnectX 系列网卡 + RoCE 集群运行 GLM-5.1-FP8 (671B MoE) PD 分离推理。本项目验证将该工作负载迁移到 AWS EFA (SRD 协议) 后，所有通信链路是否正常工作并达到同等性能水平。

PD 分离架构涉及 4 种跨节点/节点内通信模式，全部需要验证：

| 通信类型 | 协议 | 用途 |
|----------|------|------|
| TP (Tensor Parallel) | NCCL over NVLink | 节点内 GPU 间 AllReduce |
| EP (Expert Parallel) | UCCL-EP over EFA RDMA | MoE 专家 All-to-All dispatch/combine |
| KV Cache Transfer | nixl (LIBFABRIC) over EFA RDMA | Prefill → Decode KV 缓存传输 |
| PP (Pipeline Parallel) | NCCL (aws-ofi-nccl) over EFA | Prefill 节点间流水线并行 |

核心问题：**AWS EFA 能否在 MoE PD 分离推理这种极端复杂的通信负载下，达到 ConnectX + RoCE 方案的性能水平**

## 技术栈

| 层级 | 组件 | 版本/说明 |
|------|------|-----------|
| 硬件 | p5en.48xlarge × 4 | H200 × 8 + EFA × 16 per node |
| AMI | EKS-optimized AL2023 nvidia | NVIDIA driver 580.x + EFA driver + nvidia-container-toolkit |
| K8s | EKS 1.32 | Managed control plane |
| Device Plugin | NVIDIA + EFA plugin | GPU/EFA 资源注册到 kubelet |
| 推理引擎 | SGLang 0.5.10 | PD 分离架构，DeepGEMM JIT |
| KV 传输 | nixl 1.0.1 (LIBFABRIC plugin) | `--disaggregation-transfer-backend nixl` |
| MoE 通信 | UCCL-EP (DeepEP) | EFA RDMA All-to-All |
| 投机解码 | EAGLE | Decode 端加速 |

## Skill 包组成

本 skill 分为两个阶段性包：

### 1. eks-gpu-cluster-setup

**功能**: 从零构建 EKS GPU 集群，含 VPC、控制面、系统节点、GPU 节点（EFA + NVMe LVM）、Device Plugin。

**脚本**: 01 → 06，约 20-30 分钟完成。

**产出**: 4 节点 GPU 集群就绪，每节点 8 GPU + 16 EFA 设备可调度。

### 2. glm51-2p2d-serving

**功能**: 部署 GLM-5.1 PD 分离推理服务，含镜像构建、模型下载、StatefulSet 部署、Router 路由。

**脚本**: 01 → 04，冷启动约 20 分钟（含 DeepGEMM JIT 编译），热启动约 2 分钟。

**产出**: 2P2D 推理服务在线，通过 Router 统一接入。

## 启动脚本与关键参数

### Prefill 启动命令

```bash
python3 -m sglang.launch_server \
  --model-path /data/models/GLM-5.1-FP8 \
  --disaggregation-mode prefill \
  --disaggregation-transfer-backend nixl \
  --tp-size 8 \
  --pp-size 2 \
  --dp-size 1 \
  --nnodes 2 \
  --chunked-prefill-size 16384 \
  --context-length 202752 \
  --attention-backend nsa \
  --enable-nsa-prefill-context-parallel \
  --nsa-prefill-cp-mode round-robin-split \
  --deepep-mode normal \
  --moe-a2a-backend deepep \
  --moe-dense-tp-size 1 \
  --ep-dispatch-algorithm dynamic \
  --eplb-algorithm deepseek \
  --mem-fraction-static 0.85 \
  --max-running-requests 128
```

关键参数说明：

| 参数 | 值 | 含义 |
|------|---|------|
| `--tp-size 8` | 8 | Attention 切 head 维度，每 GPU 持有 8 个 attention head |
| `--pp-size 2` | 2 | 78 层平分到 2 个节点，跨节点 PP 通过 NCCL send/recv (aws-ofi-nccl → EFA) |
| `--deepep-mode normal` | normal | DeepEP 吞吐优先模式（大 batch、高带宽利用） |
| `--chunked-prefill-size 16384` | 16384 | 长序列按 16K token 分块处理，控制显存峰值 |
| `--disaggregation-transfer-backend nixl` | nixl | 使用 nixl LIBFABRIC 做 KV Cache 跨节点 RDMA 传输 |
| `--attention-backend nsa` | nsa | Native Sparse Attention（模型架构决定） |

### Decode 启动命令

```bash
python3 -m sglang.launch_server \
  --model-path /data/models/GLM-5.1-FP8 \
  --disaggregation-mode decode \
  --disaggregation-transfer-backend nixl \
  --tp-size 16 \
  --dp-size 16 \
  --nnodes 2 \
  --enable-dp-attention \
  --enable-dp-lm-head \
  --moe-dense-tp-size 1 \
  --deepep-mode low_latency \
  --moe-a2a-backend deepep \
  --ep-dispatch-algorithm dynamic \
  --eplb-algorithm deepseek \
  --context-length 202752 \
  --attention-backend nsa \
  --mem-fraction-static 0.74 \
  --max-running-requests 256 \
  --cuda-graph-max-bs 16 \
  --speculative-algorithm EAGLE \
  --speculative-num-steps 3 \
  --speculative-eagle-topk 1 \
  --speculative-num-draft-tokens 4
```

关键参数说明：

| 参数 | 值 | 含义 |
|------|---|------|
| `--tp-size 16` | 16 | EP=TP=16，256 Expert 分布到 16 GPU，每 GPU 持有 16 个 |
| `--dp-size 16` | 16 | 16 路数据并行，每 GPU 独立处理不同请求的 Decode |
| `--enable-dp-attention` | — | Attention 走数据并行，每卡完整权重，消除 AllReduce |
| `--deepep-mode low_latency` | low_latency | DeepEP 低延迟模式（小 batch、延迟敏感） |
| `--mem-fraction-static 0.74` | 0.74 | 比 Prefill 低——需为完整 Attention 权重留出显存 |
| `--speculative-algorithm EAGLE` | EAGLE | 投机解码：3 步 draft + 1 步 verify |
| `--cuda-graph-max-bs 16` | 16 | CUDA Graph 最大 batch size，减少 kernel launch 开销 |

### Router 启动命令

```bash
python3 -m sglang_router.launch_router \
  --pd-disaggregation \
  --mini-lb \
  --prefill "http://sglang-prefill-0:30082" 5555 \
  --decode "http://sglang-decode-0:30081" \
  --host 0.0.0.0 \
  --port 8000
```

`--pd-disaggregation` 启用 PD 分离模式，`--mini-lb` 使用轻量负载均衡策略。`5555` 是 Prefill 的 bootstrap port，用于 Prefill 和 Decode 之间协商 KV Cache RDMA 传输地址。

### 性能测试命令

```bash
python3 -m sglang.bench_serving \
  --backend sglang-oai \
  --base-url http://<router-endpoint>:8000 \
  --dataset-name random \
  --random-input-len 120000 \
  --random-output-len 1000 \
  --num-prompts 1024 \
  --request-rate 0.4
```

120K input + 1K output 长文本场景，1024 请求以 0.4 req/s 恒定速率发送，实际并发约 10~18 个请求。

## 测试结果

测试条件：128 请求，input 120K tokens/req，output 1K tokens/req。

### AWS EFA 详细数据（②未分卡-bug后）

| 指标 | 数值 |
|------|------|
| Successful requests | 128 |
| Benchmark duration | 382.92 s |
| Input token throughput | 40,113 tok/s |
| Output token throughput | 342.30 tok/s |
| Total token throughput | 40,456 tok/s |
| Mean TTFT | 12,499 ms |
| Mean TPOT | 17.50 ms |
| Median ITL | 52.20 ms |
| P99 ITL | 60.35 ms |
| Peak concurrent requests | 18 |

### AWS EFA vs 客户 RoCE 对比

| 指标　　　　　| 客户 RoCE (ConnectX) | AWS P5en EFA  | 差异　　　　　 | 分析　　　　　　　　　　　　　　　　　　　|
| ---------------| ----------------------| ---------------| ----------------| -------------------------------------------|
| Mean TTFT　　 | 11,904 ms　　　　　　| 12,499 ms     | AWS 高 5%　　　| Prefill 计算密集，网络非瓶颈　　　　　　　|
| **Mean TPOT** | **13.80 ms**　　　　 | **17.50 ms**  | **AWS 高 27%** | MoE 150 次小消息 per-message latency 累积 |
| Mean ITL　　　| 42.75 ms　　　　　　 | 51.07 ms      | AWS 高 19%　　 | 与 TPOT 趋势一致　　　　　　　　　　　　　|
| P99 ITL　　　 | 56.20 ms　　　　　　 | 60.35 ms      | AWS 高 7%　　　| 尾部差距显著收窄　　　　　　　　　　　　　|
| **Max ITL**　 | **434.30 ms**　　　　| **147.08 ms** | **AWS 低 66%** | **EFA SRD 多路径优势，消除极端毛刺**　　　|
| Mean E2E　　　| 25,686 ms　　　　　　| 30,405 ms     | AWS 高 18%　　 | TPOT 差距 × token 数累积　　　　　　　　　|

### 结论

- **Prefill（TTFT 差 5%）**：MoE All-to-All 全走 NVLink（EP=8 节点内），EFA 仅承担 PP send/recv，影响极小
- **Decode（TPOT 差 27%）**：EP=16 跨节点，75 层 × 2 次 = 150 次 EFA 小消息通信，per-message latency 累积是主要差距来源
- **Max ITL（AWS 好 66%）**：EFA SRD 多路径 spray 天然负载均衡，消除了 RoCE 单路径拥塞导致的极端毛刺（434ms → 147ms）
- **整体判断**：EFA 可完全承载 MoE PD 分离推理全部通信需求，Decode 延迟差距来自 per-message latency（非带宽），极端尾延迟反而更优
